# Спецификация контракта AuthService (v1)

Документ фиксирует правила взаимодействия, семантику методов, инварианты данных и модель обработки ошибок для сервиса аутентификации (`orbit.auth.v1.AuthService`) микросервисной экосистемы **Orbit AI**.

Контракт Protobuf: [`proto/orbit/auth/v1/auth.proto`](../proto/orbit/auth/v1/auth.proto)

---

## 1. Архитектурный обзор

`AuthService` отвечает за первичный вход пользователей по одноразовым кодам (OTP) без паролей, управление жизненным циклом сессий и выдачу криптографических токенов для взаимодействия с API Gateway.

```
[Клиент (Flutter / Web)] 
       │ 
       ▼
 [API Gateway] ──(Request fields: client_ip, user_agent)──► [AuthService]
                                                                   │
                                                             [PostgreSQL + Redis]
```

---

## 2. Формат и правила одноразовых кодов (OTP)

1. **Формат кода:**
   - Код представляет собой строку ровно из **6 десятичных цифр** (соответствует регулярному выражению `^[0-9]{6}$`).
   - Тип данных в Protobuf — `string`. Использование строки обязательно для сохранения ведущих нулей (например, код `"004218"` не должен превращаться в число `4218`).
2. **Время жизни (TTL):**
   - Значение TTL возвращается в поле `SendCodeResponse.expires_in_seconds` (по умолчанию 300 секунд / 5 минут).
   - По истечении TTL код считается недействительным.
3. **Однократное использование:**
   - После успешной проверки в методе `VerifyCode` код немедленно удаляется / инвалидируется. Повторный ввод того же кода невозможен.
4. **Повторная отправка и аннулирование:**
   - Предыдущий действующий код аннулируется **только при успешно принятом сервером запросе** на выпуск нового кода.
   - Запрос, отклонённый из-за действующего cooldown (`retry_after_seconds`) или лимита частоты (`ResourceExhausted`), **не изменяет и не аннулирует действующий код**. Это защищает пользователя от DoS-атаки срывом ввода при случайных повторных кликах.
   - Клиент обязан соблюдать задержку `SendCodeResponse.retry_after_seconds` (cooldown, по умолчанию 60 секунд).

---

## 3. Сессии и ротация Refresh-токенов (Token Family)

1. **Модель токенов:**
   - **Access Token:** короткоживущий JWT (Ed25519, срок действия 15 минут). Проверяется шлюзом API Gateway локально без обращения к базе данных (stateless). Точный момент истечения возвращается в `access_token_expires_at` (`google.protobuf.Timestamp`).
   - **Refresh Token:** долгоживущий криптографически стойкий непрозрачный токен (opaque string, срок действия 30–60 дней). Точный момент истечения возвращается в `refresh_token_expires_at`. В базе данных сохраняется только SHA-256 хэш токена.
2. **Атомарная однократная ротация (Atomic Single-Use Rotation):**
   - Каждый успешный вызов `RefreshToken` создаёт новую пару токенов (access + refresh) и атомарно инвалидирует использованный refresh-токен.
   - Сессия отслеживается в рамках **семейства токенов (Token Family)**.
3. **Обнаружение компрометации (Reuse Detection):**
   - Любая попытка повторного использования refresh-токена, который уже был заменён ранее в результате ротации, трактуется как компрометация сессии (попытка использования перехваченного токена).
   - Сервер **немедленно отзывает всё семейство сессии** (все токены, выданные в этой цепочке), блокируя доступ, и возвращает ошибку `Unauthenticated`.
4. **Ограничения и поведение клиента (MVP):**
   - Клиентское приложение обязано выполнять **не более одного запроса `RefreshToken` одновременно** (single in-flight refresh).
   - Клиент **не должен повторять запрос `RefreshToken` автоматически** при неоднозначном сетевом сбое (таймаут ответа). Если ответ сервера потерян в сети, а сервер уже успел выполнить ротацию токена, повторная отправка старого токена вызовет детекцию компрометации и отзыв сессии. В таком случае пользователю потребуется повторный вход по почте (OTP) — это осознанный компромисс архитектуры MVP без усложнения распределённым кэшированием результатов.

---

## 4. Поведение выхода из системы (Logout)

1. **Идемпотентность:**
   - Метод `Logout` идемпотентен. Если переданный refresh-токен уже был отозван, истёк или не найден в хранилище сессий, метод завершается успехом (gRPC status `OK`, пустой `LogoutResponse`).
   - Это гарантирует, что клиент всегда может безопасно очистить локальное состояние, а злоумышленник не может зондировать существование чужих сессий по ответу сервера.
2. **Действие Access JWT:**
   - Вызов `Logout` отзывает refresh-сессию в базе данных. Выданный ранее access JWT продолжает действовать до своего естественного истечения (максимум 15 минут), так как не проверяется по blacklist в целях сохранения высокой производительности Gateway.

---

## 5. Клиентский контекст (Client IP & User-Agent)

1. Поля `client_ip` и `user_agent` в запросах `VerifyCodeRequest` и `RefreshTokenRequest` заполняются **исключительно доверенным API Gateway**.
2. Gateway извлекает реальный IP-адрес клиента с учётом заголовка `X-Forwarded-For` только от доверенных прокси (Reverse Proxy / Load Balancer).
3. Назначение:
   - Аудит и журнал безопасности (Security Audit Log);
   - Отображение активных устройств пользователя в профиле (город, браузер, платформа);
   - Детекция аномалий (резкая смена страны/провайдера).
4. **Граница доверия:** Поле `client_ip` защищено шлюзом, однако заголовок `User-Agent` формируется на стороне клиента и лишь транслируется шлюзом в gRPC-запрос без изменений (клиент может передать произвольную строку). Поэтому данные поля используются исключительно для справочной телеметрии и аудита, но не являются фактором доверия или авторизации.

## 6. Стандартизированные коды ошибок gRPC

Сервис использует канонические статусы ошибок gRPC (`google.golang.org/grpc/codes`):

| Код ошибки | Canonical gRPC Code | Когда возвращается | Поведение клиента / Текст сообщения |
| :--- | :--- | :--- | :--- |
| **`InvalidArgument`** | `codes.InvalidArgument` (3) | Некорректный синтаксис email; длина строки OTP != 6 символов; код содержит нецифровые символы. | Отобразить ошибку валидации формы в UI. |
| **`Unauthenticated`** | `codes.Unauthenticated` (16) | Неверный код OTP; истёкший код OTP; отозванный, истёкший или скомпрометированный refresh-токен. | Для OTP возвращается единое безопасное сообщение: *«Код недействителен или истёк»*. При ошибке refresh — перенаправить на экран входа. |
| **`ResourceExhausted`** | `codes.ResourceExhausted` (8) | 1) В `SendCode`: запрос кода до истечения `retry_after_seconds`.<br>2) В `VerifyCode`: исчерпан лимит попыток ввода OTP (3–5 неудачных попыток). | 1) При `SendCode`: заблокировать кнопку до истечения таймера cooldown.<br>2) При `VerifyCode`: код окончательно аннулируется, клиенту необходимо запросить новый OTP через `SendCode`. |
| **`Unavailable`** | `codes.Unavailable` (14) | Временный сбой почтового шлюза (Resend / SMTP) или сетевой разрыв с базой данных сессий. | Для идемпотентных методов (`SendCode`, `Logout`) безопасно повторить запрос через Exponential Backoff. Для `RefreshToken` автоматический повтор запрещён. |
