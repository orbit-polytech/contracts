# Спецификация контракта AuthService (v1)

Документ фиксирует правила взаимодействия, семантику методов, инварианты данных и модель обработки ошибок для сервиса аутентификации (`orbit.auth.v1.AuthService`) микросервисной экосистемы **Orbit AI**.

Контракты Protobuf:
- [`proto/orbit/auth/v1/auth.proto`](../proto/orbit/auth/v1/auth.proto) — сервис и методы Email OTP
- [`proto/orbit/auth/v1/oauth.proto`](../proto/orbit/auth/v1/oauth.proto) — операции входа через OAuth 2.0 / OIDC
- [`proto/orbit/auth/v1/identity.proto`](../proto/orbit/auth/v1/identity.proto) — управление внешними идентичностями (Identity Linking)

---

## 1. Архитектурный обзор

`AuthService` отвечает за первичный вход пользователей по одноразовым кодам (OTP), вход через внешних провайдеров (OAuth 2.0 / OIDC: Google), безопасное управление привязанными идентичностями, ротацию сессий и выпуск асимметрично подписанных токенов Ed25519.

```
[Клиент (Web / Flutter)] 
       │ 
       ▼
 [API Gateway] ──(Request context: client_ip, user_agent, user_id)──► [AuthService]
                                                                            │
                                                                   [PostgreSQL + Redis]
```

---

## 2. Формат и правила одноразовых кодов (OTP)

1. **Формат кода:** строка ровно из **6 десятичных цифр** (`^[0-9]{6}$`). Тип — `string` (сохраняет ведущие нули).
2. **Время жизни (TTL):** по умолчанию 300 секунд (5 минут), возвращается в `SendCodeResponse.expires_in_seconds`.
3. **Однократность:** после успешной проверки в `VerifyCode` код немедленно удаляется.
4. **Повторная отправка и защита от срыва ввода:**
   - Предыдущий действующий код аннулируется **только при успешно принятом сервером запросе** на выпуск нового кода.
   - Запрос, отклонённый из-за действующего cooldown (`retry_after_seconds`) или лимита частоты (`ResourceExhausted`), **не изменяет и не аннулирует действующий код**. Это защищает пользователя от DoS-атаки срывом ввода при случайных повторных кликах.
   - Клиент обязан соблюдать задержку `SendCodeResponse.retry_after_seconds` (cooldown, по умолчанию 60 секунд).

---

## 3. Сессии и ротация Refresh-токенов (Token Family)

1. **Модель токенов:**
   - **Access Token:** короткоживущий JWT (Ed25519, 15 минут). Проверяется Gateway локально (stateless). Содержит claims: `sub` (account_id), `auth_time` (время реального подтверждения личности). Точный момент истечения возвращается в `access_token_expires_at` (`google.protobuf.Timestamp`).
   - **Refresh Token:** долгоживущий непрозрачный токен (30–60 дней). В БД сохраняется только SHA-256 хэш токена. Точный момент истечения возвращается в `refresh_token_expires_at`.
2. **Атомарная однократная ротация (Token Family):**
   - Вызов `RefreshToken` атомарно аннулирует использованный токен и выдаёт новую пару.
   - Повторное использование старого токена расценивается как кража сессии: всё семейство токенов немедленно отзывается (`Unauthenticated`).
3. **Ограничение клиента:** клиент выполняет не более одного запроса refresh одновременно (single in-flight) и не повторяет его автоматически при таймауте.

---

## 4. Поведение выхода из системы (Logout)

1. **Семантика ответа:**
   - Метод `Logout` гарантирует успешный ответ (`OK`, пустой `LogoutResponse`), если переданный refresh-токен уже был отозван, истёк или не существует в хранилище сессий. Это защищает пользователя от зондирования чужих сессий по ответам API.
   - При инфраструктурных сбоях (обрыв соединения с базой данных PostgreSQL) метод возвращает статус `Unavailable`, информируя клиент о необходимости повторить попытку.
2. **Действие Access JWT:**
   - `Logout` отзывает сессию в БД. Уже выданный Access JWT остаётся валидным до своего естественного истечения (до 15 минут), так как не проверяется по blacklist в целях сохранения высокой производительности Gateway.

---

## 5. Клиентский контекст (Client IP & User-Agent)

1. Поля `client_ip` и `user_agent` заполняются **исключительно доверенным API Gateway**.
2. Gateway извлекает реальный IP-адрес клиента с учётом заголовка `X-Forwarded-For` только от доверенных прокси.
3. Данные используются для журнала безопасности (Audit Log) и отображения активных устройств. Они не являются фактором авторизации.

---

## 6. Вход через внешних провайдеров (OAuth 2.0 / OIDC)

### 6.1. Жизненный цикл операции входа (`BeginOAuthLogin` / `FinishOAuthLogin`)
1. **Инициализация (`BeginOAuthLogin`):**
   - Gateway генерирует криптографически стойкую строку `initiator_binding` (32 байта base64url).
   - Gateway вызывает `BeginOAuthLogin(provider, client_type, initiator_binding)`.
   - `AuthService` генерирует:
     - PKCE `code_verifier` и `code_challenge` (метод S256);
     - Криптографически случайный OIDC `nonce` (для верификации ID-токена);
     - Анти-CSRF токен `state` с префиксом `login_`.
   - Вся транзакция сохраняется в Redis с TTL = 5 минут:
     `oauth:txn:<state>` $\to$ `{intent: "login", provider: "google", code_verifier, initiator_binding_hash, nonce, redirect_uri, client_type}`.
   - Gateway выставляет браузеру временную cookie: `HttpOnly`, `SameSite=Lax`, `Secure` (в prod), `Path=/api/v1/auth/oauth` со значением `initiator_binding`.
2. **Завершение (`FinishOAuthLogin`):**
   - Провайдер возвращает пользователя на зарегистрированный GET callback Gateway.
   - Gateway считывает cookie `initiator_binding` и передаёт её вместе с `code` и `state` в `FinishOAuthLogin`.
   - **Атомарная проверка до потребления (Atomic Check-and-Consume):**
     Проверка `initiator_binding`, `provider`, `intent == "login"` и срока действия операции, а также удаление/потребление транзакции выполняются **строго атомарно** (через Redis Lua-скрипт).
     **Критический инвариант безопасности:** если передан неверный `initiator_binding`, транзакция **НЕ потребляется и не удаляется**. Это исключает атаку, при которой злоумышленник с правильным `state`, но чужим binding мог бы сорвать легитимную операцию входа пользователя.
   - `AuthService` выполняет серверный обмен `code` на ID Token и Access Token провайдера по зарегистрированному `redirect_uri` с использованием `code_verifier`.
   - `AuthService` валидирует ID Token Google:
     - Проверка подписи по JWKS ключам Google;
     - Проверка срока действия (`exp`, `nbf`);
     - Проверка соответствия `iss` (`https://accounts.google.com`) и `aud` (наш `client_id`);
     - Проверка соответствия claim `nonce` сохранённому в транзакции значению.
   - `AuthService` выпускает сессию Orbit и возвращает токены и доверенный `client_type`.
   - Для Web-режима Gateway устанавливает `refresh_token` HttpOnly cookie и редиректит пользователя на чистый URL фронтенда без токенов в query.

### 6.2. Идентификация и правила регистрации аккаунтов
1. Пользователь идентифицируется **исключительно по стабильному идентификатору** `(provider, provider_subject)`.
2. **Запрет неявного слияния:** совпадение подтверждённого `email` из Google с существующим аккаунтом в Orbit **не приводит к автоматическому связыванию**.
3. **Требования к регистрации нового аккаунта:**
   - Регистрация через Google требует наличия валидного email и подтверждения **`email_verified == true`** от провайдера.
   - Если email отсутствует или не подтверждён Google, запрос на регистрацию отклоняется (`FailedPrecondition`) с требованием прохождения стандартной процедуры подтверждения почты.
4. **Повторный вход:** для уже привязанного Google-аккаунта главным идентификатором является `provider_subject`, а не совпадение email (пользователь может изменить email в Google, но его subject останется неизменным).
5. Если аккаунт с таким email уже существует в Orbit, но ещё не связан с этим Google: сервис отклоняет вход с требованием предварительно подтвердить владение существующим аккаунтом через OTP (`FailedPrecondition`).

## 7. Управление внешними идентичностями (Identity Linking)

### 7.1. Подключение способа входа (`BeginIdentityLink` / `FinishIdentityLink`)
1. **Авторизованный контекст:** метод `BeginIdentityLink` требует активной сессии пользователя (`user_id` извлекается Gateway из проверенного Access Token).
2. **Требования к подтверждению личности (`reauth_proof`):**
   - Поле `reauth_proof` содержит текущий Access JWT пользователя.
   - `AuthService` проводит строгую валидацию токена:
     - Проверка криптографической подписи Ed25519 и допустимого алгоритма;
     - Проверка ожидаемых `iss`, `aud` и срока действия `exp`;
     - Соответствие `sub == user_id`;
     - Наличие claim `auth_time` (Unix timestamp момента реальной аутентификации);
     - Значение `auth_time` не находится в будущем (с допуском дрейфа часов $\le 5$ сек);
     - Проверка окна актуальности: `now() - auth_time <= 300 секунд` (5 минут);
     - Проверка, что аккаунт не заблокирован (`is_blocked = false`).
   - При несоблюдении любого из условий возвращается `Unauthenticated` (*«Требуется повторное подтверждение личности»*).
   - **Инвариант сессий:** `AuthService` сохраняет `initial_auth_time` в сессионных данных в базе данных, благодаря чему при ротации через `RefreshToken` поле `iat` обновляется, а `auth_time` наследуется без изменений.
3. **Фиксация транзакции привязки в Redis:**
   - Сохраняется запись: `oauth:txn:<state>` $\to$ `{intent: "link", provider: "google", target_account_id: user_id, code_verifier, initiator_binding_hash, nonce, redirect_uri, max_link_time}`.
   - Предельное время завершения привязки строго ограничено наименьшим из двух значений: TTL транзакции OAuth (5 минут) и остатком разрешённого окна `auth_time`.
   - В `FinishIdentityLinkRequest` поле `user_id` отсутствует: целевой аккаунт извлекается сервером из подтверждённой транзакции в Redis.
   - Проверка `initiator_binding` и потребление транзакции выполняются атомарно (Lua script) аналогично сценарию входа.

### 7.2. Защита от отключения последнего способа входа (`UnlinkIdentity`)
1. Запрос `UnlinkIdentity` требует передачи актуального `reauth_proof` (проверка по тем же правилам).
2. **Инвариант:** у пользователя всегда должен оставаться хотя бы один способ входа (подтверждённый email для OTP или другой привязанный провайдер).
3. Попытка удалить последний способ входа отклоняется с кодом `FailedPrecondition` (*«Нельзя отключить единственный способ входа»*).
4. **Атомарность:** проверка числа способов входа и удаление выполняются внутри единой транзакции PostgreSQL с взятием блокировки:
   `SELECT pg_advisory_xact_lock(hashtext('account_identities:' || account_id::text));`

## 8. Стандартизированные коды ошибок gRPC

| Код ошибки | Canonical gRPC Code | Когда возвращается |
| :--- | :--- | :--- |
| **`InvalidArgument`** | `codes.InvalidArgument` (3) | Некорректный email, неверный формат OTP (длина != 6), пустые обязательные поля (`code`, `state`). |
| **`Unauthenticated`** | `codes.Unauthenticated` (16) | Неверный или истёкший OTP; несовпадение `initiator_binding`; недействительный ID Token провайдера; истёкший `reauth_proof` (> 5 минут); нарушение структуры claim `auth_time`. |
| **`AlreadyExists`** | `codes.AlreadyExists` (6) | Попытка привязать Google-аккаунт, который уже подключен к **другому** аккаунту Orbit (без раскрытия чужого профиля). |
| **`FailedPrecondition`** | `codes.FailedPrecondition` (9) | 1) Email из Google совпадает с существующим аккаунтом без предварительной связи.<br>2) К аккаунту уже подключен другой Google.<br>3) Попытка отключить последний доступный способ входа.<br>4) Регистрация через Google с неподтверждённым email (`email_verified = false`). |
| **`PermissionDenied`** | `codes.PermissionDenied` (7) | Аккаунт заблокирован (`is_blocked = true`). |
| **`ResourceExhausted`** | `codes.ResourceExhausted` (8) | Превышен лимит запроса OTP (cooldown) или исчерпаны попытки ввода. |
| **`Unimplemented`** | `codes.Unimplemented` (12) | Запрос нереализованного провайдера или режима (`CLIENT_TYPE_MOBILE`). |
| **`Unavailable`** | `codes.Unavailable` (14) | Сбой сети, недоступность БД или провайдера авторизации. |

## 9. Политика повторов запросов (Retry Policy)

1. **`Logout`:** допускает автоматический повтор с Exponential Backoff при сетевых сбоях (`Unavailable`), так как метод строго идемпотентен.
2. **`SendCode`:** не является идемпотентным. При неоднозначном таймауте сетевого ответа автоматический повтор **не выполняется**, чтобы не выпустить другой код и не аннулировать действующий. Отклонение по cooldown (`retry_after_seconds`) **не изменяет и не аннулирует действующий OTP**.
3. **`VerifyCode`:** автоматический повтор **запрещён**, так как сервер мог успеть проверить OTP и инвалидировать его; повторный вызов вернёт ложную ошибку `Unauthenticated`.
4. **`RefreshToken`:** строго single in-flight запрос на клиенте. Автоматический retry при таймауте **запрещён** (сервер мог выполнить ротацию, повтор вызовет Reuse Detection и отзыв сессии).
5. **`FinishOAuthLogin` и `FinishIdentityLink`:** являются строго одноразовыми операциями (atomic single-use transaction). Автоматический повтор запроса при таймауте ответа **запрещён**: если сервер успел потребить транзакцию и выпустить сессию, повторный запрос вернёт `Unauthenticated` (*«Транзакция уже использована или истекла»*). В случае сетевого обрыва клиент направляется на повторный вход через `Begin`.
